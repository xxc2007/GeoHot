## 2. 第一阶段：修复读者可见的新鲜度

文件：`packages/backend/src/publication/timeline.ts`、`items.ts`、`apps/web/app/routes/home.tsx`、`features/feed/Timeline.tsx`及对应contracts/routes/tests。

1. 补充回归：同一事实新增一篇已完成入选报道，全部池可见而事件卡保留旧anchor的场景。
2. 不新增入口、不改精选布局。在现有事件卡片中修复最新完整入选报道的更新、代表内容及时间表达；统一精选、全部、热点、主题与报刊的公开条件。不得伪造事件发生时间，排序变更须覆盖同事实转载和真实新进展回归。
3. 以明确字段表达入选/完成时间；正文引用原始发布时间。避免将补抓历史报道包装为刚发生的新闻。
4. 精选与其他公开页面共用选中、公开、中文、visible_after与完整工作流门禁；未完成文章不能因选中标记被提前展示。
5. 新增真新进展应按事实时间上浮；代表文章更换和同事实转载应保留事件语义。对疑似误归并另走正常分组复核。
6. 分别核验API、SSR HTML、浏览器导航和CDN缓存；列表缓存不超过现行60秒，长驻页面显示可控的新内容提示。查询设limit、索引及超时，不整表扫描。

验收：本样本完成后现有精选能反映最新合格更新；相同事实不会伪造新事件；无未完成条目泄露；20条真实新入选样本全部对应可读页；打开页面与新内容提示一致。

## 3. 第二阶段：建立真实产能仪表与实时优先级

文件：worker schedules、`jobs/content.ts`、`jobs/events.ts`、`operations/resource-budget.ts`、admin runs/usage读取及tests。

1. 记录每阶段每15分钟入队/完成/重试/永久失败，唯一文章通过当前revision检查的数量；不要用回执数或readiness复核数量代替新增文章。
2. 分开待运行、延时重试、执行中、需人工核验；展示优先级内最老等待，而非一个总积压数。
3. 统计采集→正文→分析→翻译→媒体→公开的p50/p95。将网络等待、provider限额、CPU/内存、数据库锁等待分开。
4. 建议新增工作预算：实时内容70%、完成已入选内容20%、历史修复10%；空闲预算可借用。设置aging防止旧任务永远饿死。这是初始试验配额，不是当前配置。
5. 当前/待出日刊优先于旧报重组；历史报修复每轮至多一期并可因资源压力延期。原历史窗口和旧版记录保留。
6. 补齐现有失败媒体的原因分类及退避；原图可以正常显示时可评估是否允许经验证的原图回退，必要图不能直接删除或标ready。

验收：同一观察窗口可计算各阶段净增量；实时队列不能被历史回填占满；unknown及受限任务不被当垃圾清除。

## 4. 第三阶段：服务器有界并发试验

禁止同时修改所有阶段。保留唯一数据库、账本、pg-boss以及R115。

1. 连续采样至少30分钟基线，检查实际systemd覆盖、模型账户限额、连接占用、swap增长、PSI、公开p95与5xx/429。
2. 先只将分析有效并发1→2，观察30～60分钟；抽取、翻译暂不变。目标是唯一合格文章产出改善，不是多发请求。
3. 通过后再单独试抽取1→2，且每站点保留速率限制、响应大小限制和超时。
4. 翻译1→2最后试；长文按已有分段、持久化和完整性验收机制处理，禁止截断。分别记录峰值内存。
5. 归组保持串行，先优化候选检索/去重；未经同事实创建竞争测试，不开放2个并发创建事实。
6. 跨分析、翻译、归组、digest、报刊建立全局模型许可与每服务/账户子额度；首次试验只新增1个全站许可，防止各队列的“2”相加失控。
7. 保留现有熔断硬线。建议加并发的较保守准入：available>=160MiB、memory full<5、I/O full<15，连续稳定10分钟；达不到就不加。available<96MiB、memory full>=10、I/O full>=30持续30秒时先撤回新增许可，保留既有硬门禁。阈值需基线校准，不写死为普遍安全值。
8. 每次试验均先滚回新增许可，再停止领取新任务，让在途任务完成。禁止靠频繁重启改变并发。

验收：相同任务类别和长度分层的合格产出有明显提升（试验目标>=20%），公开p95恶化不超过20%，没有新增OOM，429/unknown不明显上升，swap无持续爬升。否则回到前一档。

## 5. 第四阶段：模型池按能力、健康和额度并行

文件：`providers/llm.ts`、`providers/receipts.ts`、预算/健康账本及tests。

1. 多个任务分配给不同健康服务，不把同一文章复制发送给全部模型。
2. 按用途维护合格模型集合：结构化分析/筛选、完整长文翻译、事件判断、报刊组稿分别评估格式、上下文、时延及质量。
3. 只在同用途可替代集合内，根据近期成功率、时延、剩余额度可信度和在途数分配。模型别名共享同一账户时共享额度，重复别名不增加容量。
4. 明确上游拒绝且允许重试时，按现有拒绝/预算规则切换；发送后超时unknown不得立刻换模型重发。
5. 限额到期或Retry-After结束后半开少量正常任务，成功再恢复权重；不做高频额外付费探测，不永久遗忘限额解除的模型。
6. 调度优化不改当前约定推理强度。若要降档另行提出质量对照方案，不暗中修改。

## 6. 第五阶段：本机机会式协同，服务器始终独立

1. 服务器保留WORKER_ROLE=all和常驻基础能力；本机离线不能导致服务器变成只有coordinator而无人消费。
2. 先审计现有guardian/daemon/tunnel及版本指纹，不直接启用10-21旧任务或恢复历史高并发。
3. 本机首次只开1个内容辅助槽/1个抽取槽，DB与pg-boss连接各1，通过SSH回环隧道连接同一个服务器队列。稳定30～60分钟后再试2个辅助内容槽；不承诺16/32路。
4. 本机优先做正文抓取、HTML/PDF解析、图片下载转换/OG等内存与I/O工作。若现有content-executor不支持媒体队列，新增明确的media-executor角色与测试，不用all启动第二套定时器。
5. 后续更优方式：服务器短事务认领与登记回执，本机仅执行受控计算/网络任务并回交结果，减少远程持锁往返。它是后续开发项，不当成现成功能。
6. 开机/登录后自动检查版本、隧道、网络、电源、资源、R115和执行许可；检查通过才接单。可默认接电且非省电模式时运行。
7. 关机/睡眠/隧道断开先停止接单；能完成则drain。突然离线时由现有租约到期机制回收作业；付费请求进入unknown核验流程，不能宣称exactly-once。
8. 回收时限按任务类型及实测p99加余量设置。60秒无心跳可停止发放新任务，但不能60秒就重发所有在途付费任务。
9. 本机重启/睡眠恢复后不依赖Codex窗口，后台任务需有独立最小权限、日志、健康状态及一键停用；账户授权材料保持两机隔离，不复制本机设备身份到服务器。

验收：本机正常在线有额外合格产出；睡眠/断网/重启演练后服务器持续新产出，无双定时器、无双写、无无保护重发。

## 7. 实施顺序与发布

顺序：现有精选更新一致性与时间语义 → 失败媒体/今日日刊 → 指标与队列配额 → 单阶段1→2试验 → 模型用途路由 → 本机单槽协同 → 锁往返优化/媒体卸载。

每个代码阶段：最小有意义回归 → 类型检查 → 独立审查 → 分支PR与required checks → 合并 → 离机build → 资源门禁下发布 → 文件SHA/构建指纹/真实浏览器和API读回 → changelog。禁止覆盖服务器无关运行配置。

扩容不是前提；先测服务器全天自身的“完成率是否超过入队率”。如果本机关机期间长期输入仍大于服务器能力，则只能通过减少重复无效工作、按信源收益调节频率、外部可靠执行资源或后续扩容改变平衡，不能保证靠调度无限清空。

## 8. 容量估算与目标

净消化速度=合格完成任务/小时−新进入该阶段任务/小时。积压清空时间=该阶段有效待办/净消化速度，仅净速度为正时有意义；不同队列任务不能直接相加当文章数。

例：分析积压约2682、入队62/h；若完成率提高到100/h且长期维持，净消化38/h，需要约71小时。100/h仅示例不是预测，且后续抽取/翻译/媒体还须跟上。

建议试运行目标：普通新资讯从发现到完整公开p95<=30分钟，长文单独统计；已完整入选条目在现有精选中可见的更新延迟<=2分钟；三小时滚动净积压转负；本机离线期间实时内容仍有产出。未达标必须报告瓶颈，不能以总队列下降替代内容质量。
