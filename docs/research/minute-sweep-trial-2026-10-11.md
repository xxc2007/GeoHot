# 分钟扫描试验

本次仅把 content.sweep 的 cron 从每五分钟改为每分钟，及时拾取一分钟预算退避；没有增加分析 worker、并发、500 条扫描上限、100 条档案保留额、优先级、模型预算或评分门槛。其余定时任务不变。registerSchedules 仍使用 singleton 队列和唯一扫描消费者。

部署前三次真实扫描耗时 4.97、3.91、11.14 秒，只读候选选择执行约 33 毫秒；完整排队有额外写入，不能以选择查询代替全程成本。每分钟扫描最多增加六倍扫描和作业记录，不能据此保证最终吞吐或完成时间。

第 13 名 agent 已完成 worker 类型检查。一小时监测 SQL 在隔离 PostgreSQL 数据库中执行通过，初始化 pg-boss schema 后没有注册消费者，测试库已删除。PowerShell 调用器语法检查通过。根负责审阅、提交、实际部署和生产观察，本文件初始提交不声称已经上线。

生产观察使用实际 worker 启动时间明确划分上线前一小时基线与上线后的时间窗口，在 15、30、60 分钟采样。检查扫描 p95、未结束扫描与队列累积、实时内容排队和作业延迟、真实 model pass/block/selected、当前公开投影、输出拒收、预算和数据库锁等待。waiting、received、unknown 不能当成处理完成；不足一小时的累计数量不能直接与一小时基线相比。监测脚本位于本轮私有证据目录，不包含凭据。

扫描 p95 应低于 60 秒；持续两个样本有超过 120 秒的 active 扫描或待启动扫描连续累积，应排查并恢复五分钟节奏。实时延迟在样本足够时持续超过基线两倍且绝对增加超过 60 秒、数据库负载与锁等待明显恶化，亦回滚。模型请求增加但实际 pass/公开内容没有改善时，排查输出质量，不能继续增加并发。

回滚仅将 content.sweep 恢复 `*/5 * * * *`，按既有发布工作流部署并重启 worker，让 registerSchedules 更新 pg-boss 调度。保留预算、回执、现有 retry_at 与队列，不手工删除作业或强制重新购买模型答案。之后验收定时周期恢复约五分钟，并继续比较实时内容和数据库指标。
