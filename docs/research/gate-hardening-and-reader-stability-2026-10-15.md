## 二、读者面 503：这一次是我自己的验收波压出来的，而且停掉档案定时器还不够

10:43 我跑 `verify-deploy.sh`（内含 `scripts/smoke.ts` 连开 15 个 SSR 页面），同一时刻档案定时器
正在跑第 12 片的 `backfill-archive.ts`（RSS 144 MB）。之后：

- `load average` 13.64 / 15.64 / 13.63（这台机器只有 2 个 vCPU）；
- swap 从 465 MB 一路涨到 892 MB，`kswapd0`、`jbd2/sda1-8`、postgres checkpointer 全在 `D` 态；
- 读者面 `/geohot/` 24.7 s → 503，`/topics` 22.4 s，`/weekly` 503；nginx 十分钟内记了 26 条 5xx。

10:50 我停了 `geohot-archive.timer` 与正在跑的 `archive.service`。**load 掉了（13.6→6.7），
但首页还在 503/200 交替**——这说明"档案进口"只是压垮它的其中一根，热页已经被换出内存，
只要还有人在读，就得再从 swap 里捞。真正的复位是**停止我这边的探测**：11:50 之后不再有任何
自写脚本打生产，12:00 复测时首页 3.1 s、`snapshot` 0.4—1.2 s，`D` 态进程数 0，
`pg_stat_activity` 里最长那条查询只剩 1 s 级。全程没有重启任何服务，也没有杀任何进程。

⇒ 这一条把本仓库之前"503 = 档案定时器实质 24/7"的说法补完：**档案进口是常驻压力，
但把它压垮的是我的验收波与它撞在同一时刻**。修法因此不是"少采集"，而是**验收自己让路**：
`verify-deploy.sh` 第 8 节现在在跑冒烟之前 `systemctl stop geohot-archive.timer`，跑完原样 `start`
回来（只有原本是 active 的才恢复）。这一船跑完的实测：冒烟全绿，7 个读者面 200，
最慢 0.74 s，load 2.32。

## 三、配置漂移闸门：上一版有六条假绿，其中一条会把"从 GitHub 迁移"这条路自己堵死

`deploy/geohot/verify-config-drift.sh` 是我上一轮写的。这一轮独立复核（两个只读智能体，
一个评审、一个造夹具复现）挑出六条，我逐条改并每条配了一个"必然非零"的用例：

| 原缺陷 | 改法 | 用例 |
| --- | --- | --- |
| 第 1 节拿机器上的工作树当"仓库那份"，在机器上改模板就永远无漂移 | 有 git 时 `git show HEAD:` 取仓库那份；结论句子按 `have_git` 分叉 | T0/T9 |
| 第 2 节用 `-f`：`.env` 在但读不到时报"键名都有模板位" | 改 `-e`/`-r` 分叉，且读到 0 个键名也算失败 | T2 |
| 第 3/4 节挂在 `… \| sort -u` 右边是子 shell，里面的 `bad` 计数随子 shell 消失 | 先把文本收进变量，回到父进程再判红 | T1/T5/T8 |
| `redact()` 的正则连 `EnvironmentFile=` 一起吞掉，两条不同路径渲染成同一行、diff 看不见 | 只脱敏 `Environment=` 的值，路径原样比 | T1 |
| 一个单元都没装的机器报"无漂移" | 比较数为 0 时 `exit 2`，两个调用方都把非 0/1 当"跑不动" | T3 |
| 装着仓库没有模板的单元时不在核对范围内 | 用 `systemd/` 目录里实际有什么推导名单（顺带去掉与 `install-units.sh` 的重复名单），并单独报装着无模板 | T4 |

**最严重的一条不是假绿，是自堵**：第 3 节先判"文件在不在"、再判"它是不是登记过的机器侧秘密文件"，
于是照 GitHub 单独恢复的第一台机器——`workbuddy-cn.env` 还在迁移备份包里、没落到盘上——会被判
`MISSING!`，而 `install-units.sh --apply` 已经把 8 个单元装完，随后被自己这道闸门退 1。
这条修复是把"登记过的"判断挪到存在性之前（`machine-absent` 行只登记不报红），
并且保留反例：**没登记**的必需文件缺失仍然必红（T6b）。同一次复现还发现
仓库里没有任何脚本会写 `/etc/geohot/archive-cycle.conf`，于是 `install-units.sh --apply`
现在在新机器上照 `archive-cycle.conf.example` 补一份（已有的一律不动），
否则"装了定时器却没有阀门文件"会让归档退回脚本默认值 MAX_ITEMS=100/SLICES=6，
被这道闸门判红、迁移照样卡住。

另外三条是"别冤枉人"：样例里"要动再解开"的阀门解开了不许红（第 5 节改成只报
"线上用了仓库不认得的键"，不再要求集合全等）；`/etc/geohot/archive-cycle.conf` 读不到时
说"读不到"，不许报 `live=[]` 的假不一致；`install-units.sh` 现在用
`sudo env GEOHOT_APP_ROOT=…` 调用闸门，红的时候把整份（已脱敏）输出留下，
而不是只 echo 两行再把临时文件删掉。

自测脚本 `bash /tmp/ds2.sh` 十个用例全过（T0—T8 加生产 T9），生产 rc=0，
`verify-config-drift.sh` 本地/暂存/生产三处哈希 `bf9587edf369` 相同。

## 六、第三次红、以及一个可复用的恢复手法（14:00 前后）

**时间线（全部 CST）**：12:35 与 13:08 两次切迁移包时读者面还是 0.1–1.6 s；13:14–13:20 我又做了第四份包
并解包比对内容（900 MB 流式读），13:18 起 swap 冲到 1 GB；**13:37:58 那一轮归档周期（status-before →
select-slices → collect-1 → collect-2）把读者面整片打到 503**（/、/daily、/weekly、/monthly、/topics，
26.9 s / 15.4 s / 21.9 s / 15.3 s / 16.5 s）。停掉归档之后 5 分钟仍未自行恢复：load 15–16、swap 937 MB、
首页继续 503/200 交替。**这与 10:43 那次不同——那时 swap 只到 ~500 MB，停止我方探测就复位了。**

**恢复手法（实测有效，代价最小的一档）**：依次 `systemctl restart geohot-web geohot-api geohot-worker`
（worker 放最后，重启它会把在飞条目钉住最多 30 分钟，这是已知且可接受的代价）。原理是让持有换出页的
进程退出，把页直接还给系统；PG 的共享缓冲不动。实测：

| | 重启前 | 重启后 20 s | 3 分钟后 |
| --- | --- | --- | --- |
| load (1min) | 13.15 | 2.33 | **0.43** |
| swap | 984 MB | 484 MB | 634 MB |
| 首页 | 503 | 200 / 2.0 s | 200 / 2.3 s |
| 其余六个面 | 多数 503 | — | 全 200，0.12–0.80 s |

worker 自己的监视器随后打了一条 `✅ 已恢复：新内容卡住` —— 它把那段时间的内容卡顿也记下来了。

**这条要写进运维口径**：这台 891 MB 的机器在 swap 涨到 ~1 GB 之后不会自愈，重启应用进程是比
重启整机更小的一档干预（两个邻居站完全不受影响，实测根站 0.08–0.35 s、/nc15/ 0.09–0.10 s）。
八个单元都是 `enabled`，真要重启整机也能全回来——但那是需要站长点头的动作。

**待判的是"归档周期还保不保"**：从干净状态（swap ~500 MB）起跑一整轮周期，看读者面扛不扛得住；
扛得住就保留站长原来的定时器配置，扛不住就停掉并把两个数据点一起报上去。
