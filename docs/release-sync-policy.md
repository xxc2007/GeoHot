# GEOHOT 发布与三端同步规则

生效日期：2026-10-28。用户要求后续所有升级、修复和其他正式改动都提交到 GitHub，使本地源码、GitHub 仓库、服务器部署及网站对外行为对应同一个已经验证的发布版本。本规则是任务完成条件，不代表现有历史差异已经处理完毕，也不自动创建定时发布或后台同步任务。

## 什么才算同步

- 本地：需要交付的实际源文件、必要测试、依赖锁文件、公开配置和部署资料已经归入明确提交；不要求清除或提交无关工作。
- GitHub：对应提交已经 push，并按仓库规则完成 PR、审查和要求的检查，合并到发布分支。只存在本地 commit 或远端工作分支时，仍要明确说明尚未合并。
- 服务器：实际部署文件和构建来源与选定发布提交一致。构建应使用匹配的锁文件、Node/依赖环境及公开配置；部署清单同时保存源文件和实际产物的 SHA-256。不同环境生成的产物不要求与源码字节相同，应按该次发布产物清单校验。
- 网站：源站与正式域名实际返回的页面/API、静态资源指纹和新行为符合该次发布。文件已上传、进程 active、Git HEAD 或 health 200 不能单独证明网站已经使用该版本。

三端同步不等于源码、构建文件、数据库与所有部署机器字节完全相同，也不等于历史文章、翻译和积压全部完成。受控文件应匹配对应发布内容；私有环境和正常运行数据保留各自边界。

## 正常发布步骤

1. 核对远端发布分支、本地改动与生产当前版本/哈希。存在未提交生产热修复或其他协作改动时，先列出差异，不能直接覆盖整棵目录。
2. 以可信远端状态建立或复用隔离分支，只纳入本次授权范围的实际源码、必要测试和说明。真实配置值、密钥、授权材料、数据库、缓存和诊断日志不得进入公开仓库；配置字段变化提交模板与非敏感说明。
3. 根据变化运行必要验证和要求的检查。没有新代码、失败或未解决疑点时，不为同一内容反复做全套测试、备份或付费验证。
4. commit、push，创建或更新 PR，经过独立审查与要求的 CI 检查后合并。保留完整历史，不强制覆盖远端。发布目标是明确的已合并提交，不笼统使用“最新”作为版本证据。
5. 按现有服务器资源、读者保护、停止责任和 R115 条件部署。资源不足时延期；仅在需要加载新代码/构建时重启相关服务，保留在途付费请求的优雅收尾与已核验前版。内容就绪门槛、单库/队列/账本和 pending/unknown 恢复保护不得因同步操作放松。
6. 读回服务器受控源文件/部署产物哈希、静态资源指纹和必要的正式网页/API 行为；确认缓存没有继续提供旧版本。按变化需要做真实浏览器验收，不能只读 health。
7. 对读者或管理员可感知的功能、修复、模型和统计口径变化，同轮更新 industry/changelog.json，保留原记录，按实际上线时间排序并更新 latestVersion；纯内部文档或流程约束由 Git 提交和内部发布记录说明，不伪造产品功能上线。
8. 在最终报告中提供 GitHub PR/发布提交、实际部署范围和验证范围；尚未合并、尚未部署、缓存仍旧或其他差异必须列为未完成。

## 紧急修复的收尾

读者访问或工作流故障时，可以先按已有维护约束部署最小补丁；这只是部署顺序的例外。必须在同一轮任务中将实际生产修复回收为源代码、必要测试和日志，补齐提交/PR/合并，再复核服务器与网站。不能只保存 patch 或临时目录就结束。外部故障或检查阻止回收时，保留可恢复证据并明确阻断与差异，不宣称整体发布完成。

数据文件热更新无需为了“有一次重启”而重启业务；应验证文件 mtime/读取缓存、公开 API、页面与通知版本确实更新。只为代码改动之外的文档建立提交时，也不把新 Git 提交号冒充已经部署的业务版本。

## 发布记录的最小字段

- 变更范围、实际部署时间与本次更新日志条目（适用时）。
- PR、发布分支与发布 commit；若存在紧急部署顺序例外，写清回收后的对应提交。
- 发布清单：受控源文件、锁文件及实际部署产物的哈希；私有配置只记录模板版本和字段验证结果，不保存秘密值或可用于猜测秘密的哈希。
- 服务器已部署内容、所需服务是否加载新版本，正式网页/API 和浏览器验收结果。
- 通过与未覆盖范围、仍在处理的历史工作、明确未同步差异及回滚依据。

当前规则文档与 AGENTS.md 的同步只证明这些指导文件一致。此前尚未完整回收的生产源码仍需逐项对照和补提交；不得因此重写旧 health/release 标记、丢弃本地改动或强行重部署来制造“全部同步”。
